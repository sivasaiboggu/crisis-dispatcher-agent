# Crisis Dispatcher Agent — Deepened Plan (SaaS level, demoable in 24–48h)

## 1. What it is

A simulated emergency-dispatch training board. A scenario script feeds
simulated incident reports into a real decision pipeline — triage,
prioritisation, resource matching, dispatch — and the board shows every
decision on a live map with a one-line, plain-language rationale.

**Honesty, first:** this is a SIMULATION. There is no live emergency
feed, no connection to real 108/112 services, and no real ambulances.
Every incident is generated by a scenario script. The screen says
"SIMULATED" at all times, and every screen carries the line
"Simulated training scenario — no real emergencies." Nothing in the
demo may present a simulated incident as real, and nothing may imply
the system could dispatch real emergency services. The honest
achievement is the decision pipeline, which is real, deterministic,
and demonstrable.

## 2. Who it is for

- **Hackathon judges** — the 2-minute demo (Section 9) is the product.
- **Training officers / dispatch trainees** — the board is a trainer:
  run a scenario, watch the pipeline decide, inject a surprise
  incident, and read why each unit was chosen.
- **Future buyer (v2):** a computer-aided dispatch (CAD) vendor who
  would plug the same pipeline into a real feed. v1 proves the
  pipeline; it does not claim the integration.

## 3. Design identity (this project's alone)

- **Palette:** amber `#D97706` on dark slate (`#0F172A` base,
  `#1E293B` panels, `#334155` borders). Amber is the working colour:
  severity, active states, the SIMULATED badge. No other accent.
  Severity scale: P1 `#DC2626`, P2 `#D97706`, P3 `#CA8A04`,
  P4 `#64748B`. Accent under 10% of any screen.
- **Type:** Barlow (UI, 400/500/600/700), Barlow Condensed 600/700
  (board headings, incident codes), IBM Plex Mono (times, scores,
  ETAs — tabular figures everywhere numbers matter). Self-hosted
  woff2, vendored in `vendor/fonts/`; no webfont dependency at runtime.
- **Signature idea — the severity rail:** every incident row, map
  marker, and dispatch entry carries a 3px severity edge on its left.
  The board reads as a ledger, not a card grid.
- **References (from the playbook):** Mobbin (dense ops-dashboard
  screens — map centre, queue left, log right), Linear (dark board,
  1px borders, tabular numbers, plain copy), Raycast (dense
  command-style lists, keyboard-first). Borrowed: spacing, type scale,
  the three-column operations layout. Not borrowed: any colour or
  component verbatim.
- **Motion:** 150–250ms, transform/opacity only. Markers move;
  the feed prepends; the log fills. No staggered entrances, no
  shimmer, no glow.
- **Copy:** plain human words. "Unit A-3 dispatched: nearest ALS
  unit, 4 min ETA, 3 critical casualties." No "seamless",
  "supercharge", "elevate", no sparkle symbols.

## 4. Stack (verified, 23 Nov 2026)

- **Leaflet 1.9.4** (stable, released 18 May 2023; 2.0.0-alpha.1 is
  prerelease — not used). Vendored in `vendor/leaflet/` so the demo
  runs with no CDN dependency. Map tiles: OpenStreetMap standard
  tiles `https://tile.openstreetmap.org/{z}/{x}/{y}.png` with the
  required `© OpenStreetMap contributors` attribution, per the OSMF
  Tile Usage Policy (HTTPS only, attribution visible, no bulk
  download, browser caching left on). A vector street grid of the
  fictional city is drawn over the map, so the board stays readable
  when tiles cannot load (venue Wi-Fi); the map corner then says
  "Map tiles unavailable — street grid shown".
- **Gemini (optional):** `POST
  https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent`,
  `x-goog-api-key` header, response text at
  `candidates[0].content.parts[].text`. Key is pasted by the user in
  Settings and stored in `localStorage` only. No key exists in this
  build; the app is fully demoable without one.
- **No build step, no server in v1.** Plain HTML/CSS/JS, one static
  app. Deliberate deviation from the original plan's Next.js +
  FastAPI: a static app runs from `file://` or any static host with
  zero cold starts, which is the single biggest demo risk in the
  original plan (Render free-tier cold start ~50s). The pipeline
  (triage → prioritise → dispatch → explain) is implemented as four
  plain functions mirroring LangGraph nodes, with the same inputs
  and outputs, so a FastAPI + LangGraph backend can replace the
  in-browser engine without changing the UI contract. That backend
  is documented as v2 in the README.
- **State:** in-memory + `localStorage` for Settings only. No
  database in v1; the scenario script is the data source.

## 5. Data model

```
Incident { id, code, type, severity (P1–P4), triageScore,
  scoreBreakdown {type, casualties, trapped, surge},
  casualties, trapped, lat, lng, place, status
  (incoming|triaged|assigned|on-scene|resolved),
  reportedAt (sim seconds), source: "scenario" | "injected" }
Unit { id, kind (ALS|BLS|fire|police|rescue), capabilities [],
  baseLat, baseLng, lat, lng, status
  (available|dispatched|on-scene|returning|off-duty),
  assignedIncidentId, etaMin }
Dispatch { id, incidentId, unitId, decidedAt, etaMin,
  rationale, rationaleSource ("rule"|"gemini"),
  alternatives [{unitId, reason}] }
Scenario { id, name, blurb, durationSec, events
  [{t, incident}] }
```

## 6. Decision pipeline (deterministic, zero LLM calls)

1. **Triage** — `triageScore = typeWeight + min(casualties × 8, 40)
   + (trapped ? 15 : 0) + (casualties ≥ 10 ? 10 : 0)`, capped at 100.
   Type weights: collapse 30, fire 25, hazmat 22, road-traffic 20,
   medical 18, crime 12. Priority: ≥70 P1, ≥45 P2, ≥25 P3, else P4.
2. **Prioritise** — queue sorted by triage score desc, then
   reported time asc. A P1 never waits behind a P4.
3. **Dispatch (match)** — eligible units = available units whose
   capabilities cover the incident's required capability
   (collapse → rescue/ALS; fire/hazmat → fire; road-traffic/medical
   → ALS/BLS; crime → police). Nearest by haversine distance;
   ETA = 2 + distance / 0.55 km-per-min (≈33 km/h city speed),
   rounded. Tie-break: lower ETA, then unit id. The matcher also
   records the nearest *rejected* units and why (e.g. "A-1 is 1 min
   closer but has no ALS capability") — that is the explanation for
   the case where the nearest unit was not chosen.
4. **Explain** — default: a rule-based rationale template, always
   available, always labelled "Rule-based rationale". Optional:
   one Gemini call per dispatch rewrites the same facts in plainer
   language, labelled "Gemini rationale". If the call fails, is
   slow (>8s timeout), or no key is set, the rule text stands.
   Scoring and matching never depend on the model.

## 7. Feature set (v1, all working)

- Three scripted scenarios on a fictional Hyderabad grid (real city
  geography, fictional street-level incident points):
  1. **Market building collapse** (headline, ~90s): 12-casualty
     collapse + 3 concurrent minor incidents.
  2. **Monsoon evening** (~120s): 6 staggered incidents.
  3. **Quiet night** (~60s): 2 minor incidents.
- Live map: Leaflet, OSM tiles + vector street grid, severity
  markers, unit markers that move toward their incident, ETA
  countdowns, click a marker to open the incident.
- Incident queue: sorted by triage score, severity rail, casualties,
  status, reported time. Click for the detail card: score breakdown,
  required capability, alternatives considered, dispatch history.
- Units panel: all 10 units (4 ALS, 2 BLS, 2 fire, 2 police,
  1 rescue), status, current assignment, ETA. Unit lifecycle:
  available → dispatched → on-scene → returning → available.
- Dispatch log: timestamped entries with rationale + source tag
  (rule/gemini), newest first.
- What-if control: "Inject incident" — pick type, casualties,
  trapped, and one of four fictional locations; the pipeline
  re-triages and re-prioritises live, including stealing no unit
  from a higher-priority incident (it takes the next-best available
  unit and says so).
- Sim controls: scenario picker, Start / Pause, speed 1×/2×/4×,
  Reset, sim clock. Everything pre-seeded; the demo starts from
  one click.
- Settings: Gemini API key (paste, save to localStorage only,
  clear, test with a one-word call), model shown as
  gemini-2.5-flash, status line stating which rationale source is
  active. No key → the status line says so plainly.
- Stats strip: incidents in, P1 unassigned, units available,
  dispatched, average ETA.
- Honesty chrome: "SIMULATED" badge in the top bar at all times;
  footer line on every view: "Simulated training scenario — no
  real emergencies."; Settings explains the key never leaves the
  browser except to Google's API.
- `?shot=1` URL parameter: loads the headline scenario
  fast-forwarded to a mid-flood state for screenshots and for a
  cold-start demo if the timer cannot run.

## 8. Complete user flow, end to end

1. Open `index.html`. Board loads with the headline scenario
   pre-selected, 10 units available on the map, queue empty, log
   showing "Scenario ready — press Start". SIMULATED badge visible.
2. Press **Start**. Sim clock runs. At t=0 the collapse report
   arrives: queue shows INC-101, P1, score 97, "12 casualties,
   4 trapped". The matcher assigns the nearest rescue/ALS unit
   (R-1 or A-3); the log line reads "R-1 dispatched to INC-101:
   nearest rescue unit, 4 min ETA, 12 casualties, 4 trapped
   (rule-based rationale)". The unit marker moves.
3. At t=8, 18, 30 the concurrent incidents arrive; each is triaged
   instantly and dispatched to the next-best available unit. The
   queue re-sorts; the map gains markers.
4. The user clicks the collapse marker. The detail card shows the
   score breakdown (collapse 30 + casualties 40 + trapped 15 +
   surge 10 = 95) and
   "A-1 was 1 min closer but has no ALS capability" style
   alternatives.
5. At t≈45 the user presses **Inject incident**, adds a fire with
   5 casualties at Tank Bund Rd. It lands as P1/P2, takes the
   nearest available fire unit, and the log says so.
6. Units arrive (ETA hits 0 → on-scene), dwell, return to base,
   become available again. Resolved incidents move to the bottom
   of the queue with status "resolved".
7. The user opens **Settings**, pastes a free Gemini key, saves.
   The status line changes to "Gemini rationale on". The next
   dispatch log line is labelled "Gemini rationale" and reads in
   the model's words; the facts (unit, ETA, casualties) are the
   same, because they come from the engine, not the model.
8. Press **Reset** to run it again, or pick another scenario.
   Nothing in the flow needs a network call except OSM tiles
   (optional) and Gemini (optional).

## 9. Two-minute demo script

- **0:00–0:15 — Setup in one line.** "This is a simulated training
  scenario — no real incidents. Watch the map." Press Start.
- **0:15–0:45 — The flood.** Incidents appear one by one; triage
  scores appear instantly. Point at the collapse marker: "12
  casualties, building collapse — ranked first automatically."
- **0:45–1:20 — The dispatch.** Units move on the map; the log
  fills with rationale lines. Read one aloud: "Unit A-3, nearest
  ALS, 4-minute ETA." Then inject a surprise fire live to show
  re-prioritisation.
- **1:20–1:50 — The explanation.** Open the collapse card and show
  the reasoning chain: triage score, alternatives considered, why
  the nearest unit was *not* chosen for one case — it lacked ALS
  capability.
- **1:50–2:00 — Close.** "Deterministic matching, LLM explanation,
  fully simulated. The same pipeline could plug into a real CAD
  feed — but today it's a trainer."

## 10. Risks and fallbacks

- **Gemini quota / no key:** rule-based rationale is the default;
  the demo loses only polished wording, never function.
- **Map tiles / venue Wi-Fi down:** vector street grid + vendored
  Leaflet keep the board readable; the corner note says tiles are
  unavailable. The whole app runs from `file://`.
- **Scenario timing slips:** `?shot=1` gives a mid-flood board
  instantly; Reset re-runs deterministically.

## 11. What v1 is not (honest limits)

- No Next.js/FastAPI server, no SQLite, no LangGraph runtime —
  the pipeline is four plain functions with the same node
  contract; the server is v2 (see README).
- No real-time feed, no user accounts, no persistence beyond
  Settings, no multi-city support, no accessibility audit beyond
  keyboard-reachable controls and visible focus states.
- Unit movement is straight-line interpolation, not road routing;
  ETAs are distance-based estimates, not traffic-aware.
