# Crisis Dispatcher Agent

A simulated emergency-dispatch training board. A scenario script feeds
simulated incident reports into a real decision pipeline — triage,
prioritisation, resource matching, dispatch — and the board shows every
decision on a live map with a one-line, plain-language rationale.

## Honesty first — read this before the demo

**This is a SIMULATION.** There is no live emergency feed, no
connection to real 108/112 services, and no real ambulances. Every
incident is generated by a scenario script. The screen says
**SIMULATED** at all times, and the footer on every view reads
"Simulated training scenario — no real emergencies." Nothing here may
be presented as a real incident, and nothing implies the system could
dispatch real emergency services. The honest achievement is the
decision pipeline, which is real, deterministic, and demonstrable.

## Run it

No build step, no server, no key needed. Open `index.html` in any
modern browser — or serve the folder with any static host
(`python3 -m http.server`, GitHub Pages, Vercel).

1. Press **Start scenario**. The collapse report arrives at 00:00 and
   the pipeline triages and dispatches within a second.
2. Click any incident (queue or map marker) to see its triage
   breakdown, assigned unit, and the alternatives the matcher
   considered.
3. Press **Inject incident** mid-run to add a surprise report and
   watch the queue re-prioritise.
4. **Settings** takes an optional free Gemini API key (see below).

`?shot=1` loads the headline scenario fast-forwarded to 00:40 with
four incidents and four dispatches — for screenshots and for a
cold-start demo. `?shot=1&detail=1` also opens the top incident's
detail card; `?shot=1&inject=1` opens the inject dialog.

## The decision pipeline (deterministic, zero LLM calls)

Implemented in `src/engine.js` — four plain functions, mirroring
LangGraph nodes, with the same inputs and outputs:

1. **Triage** — `score = typeWeight + min(casualties × 8, 40) +
   (trapped ? 15 : 0) + (casualties ≥ 10 ? 10 : 0)`, capped at 100.
   Type weights: collapse 30, fire 25, hazmat 22, road-traffic 20,
   medical 18, crime 12. Priority: ≥70 P1, ≥45 P2, ≥25 P3, else P4.
2. **Prioritise** — queue sorted by score desc, then reported time
   asc. A P1 never waits behind a P4.
3. **Dispatch** — eligible units are available units whose
   capabilities cover the incident (collapse → rescue/ALS, fire →
   fire, road-traffic/medical → ALS/BLS, crime → police). Nearest by
   haversine distance; ETA = 2 + distance / 0.55 km-per-min
   (≈33 km/h city speed). The matcher records the nearest *rejected*
   units and why — e.g. "B-1 is 2 min away but has no rescue/ALS
   capability" — which is the explanation for the case where the
   nearest unit was not chosen.
4. **Explain** — a rule-based rationale template is the default and
   is always available. Optionally, one Gemini call per dispatch
   rewrites the same facts in plainer language. If the call fails,
   times out (8 s), or no key is set, the rule text stands. Scoring
   and matching never depend on the model.

## Gemini rationale (optional)

Settings → paste a free Gemini API key from Google AI Studio. The key
is stored in the browser's `localStorage` only and is sent only to
Google's API when a dispatch happens. Model: `gemini-2.5-flash`
(`POST https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent`,
`x-goog-api-key` header). The prompt carries the engine's exact
numbers; the model only rewords them. Each log line is tagged
**Rule-based rationale** or **Gemini rationale** so you can always
tell which one you are reading. Without a key the demo works fully —
the footer says so plainly.

## Scenarios

Three scripted scenarios on a fictional Hyderabad grid (real city
geography, fictional street-level incident points), 11 units
(4 ALS, 2 BLS, 2 fire, 2 police, 1 rescue):

| Scenario | What happens |
| --- | --- |
| Market building collapse (headline) | 12-casualty collapse + 3 concurrent incidents, ~90 s |
| Monsoon evening | 6 staggered incidents over ~2 min |
| Quiet night | 2 minor incidents |

Unit lifecycle: available → dispatched → on-scene → returning →
available. A freed unit re-tries the highest-priority unassigned
incident. Marker movement is time-compressed for training (6
sim-seconds per ETA minute); ETAs shown are the engine's estimates.

## Map

Leaflet **1.9.4** (stable, released 18 May 2023; 2.0.0-alpha.1 is
prerelease and is not used), vendored in `vendor/leaflet/` so the
demo has no CDN dependency. Tiles: OpenStreetMap standard tiles
`https://tile.openstreetmap.org/{z}/{x}/{y}.png` with the required
`© OpenStreetMap contributors` attribution, per the OSMF Tile Usage
Policy (HTTPS only, attribution visible, no bulk download). A vector
street grid of the fictional city is drawn over the map, so the board
stays readable when tiles cannot load (venue Wi-Fi); the map corner
then says "Map tiles unavailable — street grid shown". Fonts (Barlow,
Barlow Condensed, IBM Plex Mono) are self-hosted woff2 in
`vendor/fonts/` — no webfont dependency at runtime.

## Design

Amber `#D97706` on dark slate, Barlow + IBM Plex Mono for numbers.
Signature idea: the **severity rail** — every incident row, map
marker, and dispatch entry carries a 3px severity edge on its left.
References: Mobbin (dense ops-dashboard layout), Linear (dark board,
1px borders, tabular numbers). No gradients, no glows, no sparkle
symbols, plain human copy.

## Tests

`node --test tests/engine.test.js` — **33 tests, 33 pass, 0 fail**.
Covers triage arithmetic and bands, haversine distances against
known values, ETA math, matcher capability filtering and the
nearest-rejected explanation, queue ordering, rationale wording,
roster coverage, scenario validity (events in time order, known
places, every event dispatchable with the real roster), and the
Gemini layer's model/endpoint contract (no key, no network).

## Two-minute demo script

- **0:00–0:15** — "This is a simulated training scenario — no real
  incidents. Watch the map." Press Start.
- **0:15–0:45** — Incidents appear one by one; triage scores appear
  instantly. Point at the collapse marker: "12 casualties, building
  collapse — ranked first automatically."
- **0:45–1:20** — Units move on the map; the log fills with
  rationale lines. Read one aloud: "Unit A-3, nearest ALS,
  4-minute ETA." Then inject a surprise fire live to show
  re-prioritisation.
- **1:20–1:50** — Open the collapse card: score breakdown,
  alternatives considered, why the nearest unit was *not* chosen
  for one case — it lacked ALS capability.
- **1:50–2:00** — "Deterministic matching, LLM explanation, fully
  simulated. The same pipeline could plug into a real CAD feed —
  but today it's a trainer."

## Honest limits

- No Next.js/FastAPI server, no SQLite, no LangGraph runtime in v1.
  The pipeline is four plain functions with the same node contract;
  a static app was chosen deliberately so the demo runs from
  `file://` with zero cold starts (the original plan's biggest demo
  risk). The server is v2, below.
- No real-time feed, no user accounts, no persistence beyond
  Settings, no multi-city support.
- Unit movement is straight-line interpolation, not road routing;
  ETAs are distance-based estimates, not traffic-aware.
- Gemini rationale is a rewording layer only — it never supplies
  facts, and the demo never fakes a rationale when no key is set.
- The headless-Chrome screenshots show the offline street grid, not
  OSM tiles, because this VM's headless Chrome cannot reach external
  HTTPS. On a normal network the OSM tiles load under the grid.

## v2 ideas

FastAPI + LangGraph backend with SQLite (same pipeline contract);
live SSE feed; road-routed ETAs via OSRM; multi-scenario editor;
trainee scoring (did the human dispatcher beat the agent?);
exportable after-action report; keyboard-first operation.
